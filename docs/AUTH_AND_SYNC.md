# Аккаунты и облачная синхронизация

## Модель сессии

- пароль хешируется `scrypt` с уникальной солью и никогда не возвращается клиенту;
- access-токен — непрозрачные 32 случайных байта со сроком 15 минут;
- refresh-токен — непрозрачные 48 случайных байт со сроком 30 дней;
- PostgreSQL хранит только SHA-256 хеши токенов;
- refresh всегда ротирует оба токена, поэтому повторное использование старого refresh-токена отклоняется;
- logout отзывает текущую сессию, удаление аккаунта каскадно удаляет все сессии и данные;
- auth API ограничен по частоте и не кешируется.

На iOS и Android refresh-токен хранится через Expo SecureStore в Keychain/Keystore с доступом только на текущем устройстве. Access-токен существует только в памяти JavaScript-процесса. Несекретный progress cache и offline-очередь используют AsyncStorage. В web-preview refresh-токен хранится только в памяти вкладки.

## Поток синхронизации

1. Изменение сразу применяется к Zustand и записывается в AsyncStorage outbox.
2. Каждая операция содержит уникальный id, время, тип, target и конечное желаемое значение.
3. Клиент отправляет операции пакетами до 100 элементов при активном приложении или восстановлении сети.
4. PostgreSQL блокирует snapshot пользователя, регистрирует новые idempotency keys и атомарно обновляет версию.
5. Клиент удаляет только подтверждённые операции и заменяет локальный snapshot результатом сервера.

Желаемое значение (`saved: true`), а не команда `toggle`, делает повторную доставку безопасной. Конфликт между устройствами разрешается порядком получения сервером: последняя принятая операция для сущности определяет состояние. Если облако пустое, первый вход переносит существующий локальный прогресс пользователя.

Завершения учебных сессий используют отдельную постоянную очередь. Клиент оптимистично отмечает сессию, сервер регистрирует `actionId`, атомарно обновляет мастерство и возвращает пересчитанный snapshot. После потери сети очередь отправляется по порядку при foreground/background переходе или восстановлении соединения. Стабильные id незавершённых сессий позволяют безопасно доставить несколько offline-завершений подряд.

## Privacy-функции

- `GET /v1/account/export` возвращает аккаунт, cloud progress и snapshot персональной подготовки;
- экспорт вызывается пользователем из приложения через системный Share Sheet;
- `DELETE /v1/account` требует действующий access-токен и повторное подтверждение паролем;
- после удаления приложение очищает SecureStore, локальный progress и outbox этого аккаунта.

## Ограничения перед production

- production backend обязан работать только через HTTPS;
- email verification, восстановление пароля и Google/Apple OAuth потребуют почтового провайдера и production client IDs;
- текущий rate limiter хранится в процессе; для нескольких backend-инстансов потребуется общий Redis/edge limiter;
- in-memory repository подходит только для разработки и теряет аккаунты после перезапуска;
- биометрическое чтение SecureStore должно дополнительно проверяться на реальных устройствах перед beta-релизом.
